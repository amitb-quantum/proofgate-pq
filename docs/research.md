## Cryptographic boundary

Implemented suites are `ed25519-v1` (classical comparison), `mldsa65-v1` (PQC), and
`ed25519-mldsa65-v1` (default dual mode). All identity roles use the pinned suite, including
requester and result signer. Otherwise a classical-only authentication root would undermine
the intended PQ authorization chain. Independent component keys are generated by providers.

Both hybrid components sign the identical domain-prefixed canonical envelope containing
suite, signer and body. Verification requires exactly the registry's components and locally
pinned keys. Ed25519 is not quantum-resistant. ML-DSA's standardization is not evidence that
this protocol, Python application, provider build or installation is FIPS validated.
No FIPS 140 module-validation claim is made. No new primitive is implemented.

SHA-384 is an application digest choice; this does not establish a formal end-to-end
security category. The dual mode's robustness is an engineering design requiring analysis,
not a claimed proof that arbitrary composition inherits the strongest component.

SLH-DSA is deliberately not implemented: the selected PyCA 49.0.0 installation has no
`slhdsa` module, and adding a subprocess/FFI provider solely for feature count increases
review surface. This is a documented scope choice, never a silent runtime fallback.
Unknown or unavailable required suites must fail with a structured error.

Standards define primitives; this repository defines a nonstandard authorization protocol.
Process isolation, deterministic policy checks and replay durability are engineering
mechanisms/assumptions. Test outcomes demonstrate specific executions, not universal security.
